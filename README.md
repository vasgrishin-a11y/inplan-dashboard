# In.Plan Dashboard

Одностраничный дашборд планирования спроса: спрос и покрытие, дефицит и упущенная
маржа, мощности, штрафы, сравнение версий планов, качество данных.

Источники данных:

1. **ClickHouse** — результаты прогонов планировщика: базы `data_public_N`
   (версии планов), таблицы `marking_demand`, `demand_coverage`, `capacity_view_sp`,
   `rescapacity`, `demand_cost`. Подключение — напрямую из браузера по HTTP
   (кнопка «⚡ ClickHouse» в шапке).
2. **PostgreSQL** — входной (неограниченный) спрос: таблица `independentdemand`
   (колонка `demandqty`) в схемах `public_N`. Браузер не умеет открывать TCP к
   Postgres, поэтому запросы обслуживает backend-прокси **`server.js`** этого
   репозитория (тот же паттерн, что и у дашборда opti).

Соответствие версий между источниками: база ClickHouse `data_public_2` ↔ схема
PostgreSQL `public_2` (снимается префикс `data_`, регистр не важен).

## Быстрый старт

```bash
npm install
npm start        # → http://localhost:8080 (PORT/HOST настраиваются переменными окружения)
```

`server.js` одновременно раздаёт статику дашборда и API PostgreSQL:

| Эндпоинт              | Назначение                                                        |
|-----------------------|-------------------------------------------------------------------|
| `GET  /api/health`    | проверка, что backend жив                                         |
| `GET  /api/pg/defaults` | хост/порт/база PG по умолчанию для формы подключения            |
| `POST /api/pg/schemas` | схемы, в которых есть таблица `independentdemand`               |
| `POST /api/pg/unc`    | агрегат неограниченного спроса: `{schema, gran}` → `Σ demandqty` итогом и по периодам |

Логин/пароль PostgreSQL вводятся в модалке подключения (блок «PostgreSQL —
independentdemand»), уходят в теле каждого запроса и нигде на сервере не
сохраняются; в браузере — автосессия на 4 часа (кнопка «Забыть PG-сессию»).

Открытие `index.html` напрямую (или со статического хостинга) тоже работает:
ClickHouse-подключение не требует backend. Для PostgreSQL в этом случае укажите
в модалке поле **«Backend»** — URL запущенного `server.js` (при `file://`
подставляется `http://localhost:8080`).

## Неограниченный спрос — источники

1. **PostgreSQL** через backend-прокси — схема `public_N` по CH-базе
   `data_public_N`. Таблица `independentdemand` физически лежит только там
   (в ClickHouse её нет — дашборд туда и не ходит);
2. фолбэк: покрытый + непокрытый (`fullfilleddemandqty + unfullfilleddemandqty`)
   из `demand_coverage` — версия помечается в статусе загрузки, в «Сравнении
   версий» и во вкладке «Данные и качество».

Какой бы источник ни сработал, значение лежит в `agg.totals.cov.demUnc`, и все
разделы читают одно определение; фактический источник фиксируется в
`agg.totals.uncDetail` («PostgreSQL · public_2»).

## Тесты

```bash
npm test
```

Node-тесты: jsdom-регрессии вкладок и коннекторов (`tests/*.test.mjs`) плюс
юнит-тесты backend (`tests/server.test.mjs`, DB-слой инжектится через
`createApp({connect})`). Живая PostgreSQL/ClickHouse для прогона не нужна.

## Разворачивание в контуре

Процесс Node должен видеть и PostgreSQL (для API), и быть доступным
пользователям дашборда. Типовой вариант — рядом с базой PG в том же
Kubernetes-контуре: `HOST=0.0.0.0 PORT=8080 npm start`. ClickHouse браузер
пользователя подключает напрямую — сетевой доступ к нему нужен с машин
пользователей, к backend — только к порту Node.
