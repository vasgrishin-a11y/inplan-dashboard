# In.Plan Dashboard

Одностраничный дашборд планирования спроса: спрос и покрытие, дефицит и упущенная
маржа, мощности, штрафы, сравнение версий планов, качество данных.

Источники данных:

1. **ClickHouse** — результаты прогонов планировщика: базы `data_public_N`
   (версии планов), таблицы `marking_demand`, `demand_coverage`, `margin_sales`,
   `capacity_view_sp`, `rescapacity`, `demand_cost`, `demand_cost_ti`. Подключение — напрямую из
   браузера по HTTP (кнопка «⚡ ClickHouse» в шапке).

   **Итоговые финансы** (пересчёт 2026-10-07): «Валовая выручка» приоритетно
   считается по **ценам спроса**: `Σ fullfilleddemandqty × цена` — выполненный
   объём `demand_coverage` × цена из справочника `demand_cost` / `demand_cost_ti`
   (колонка цены — `nondelcostrate`, при её отсутствии/пустоте — первый
   подходящий кандидат; сшивка по `item + loc + dmdstream + demandtype` +
   период `periodid`/`date`/`datefr`; нет цены в периоде строки — берётся
   ближайший период; периодные цены `demand_cost` приоритетнее безпериодных
   `demand_cost_ti`). «Валовая маржа» = `Σ total_margin` и себестоимость при
   этом **не пересчитываются**. Если цены не сопоставились (таблиц нет, нет
   колонки цены, ноль смэтченных строк) — выручка считается по **`margin_sales`**
   (`Σ revenue`, пересчёт 2026-10-06), а при её недоступности/пустоте — честный
   фолбэк на итоги `marking_demand`. Значения показываются в карточках верхнего
   ряда разделов и в сравнении версий; таблицы и графики остаются на
   детализации заказов `marking_demand`. Фактический источник выручки виден в
   подписи карточки (`revSrc`) и теге матрицы версий, качество сшивки (доля
   объёма с ценой, «ближайший период», нулевые цены, сверка с прежней цепочкой)
   — во вкладке «Данные и качество».
2. **PostgreSQL** — входной (неограниченный) спрос: таблица `independent_demand`
   (колонка `demandqty`) в схемах `public_N` базы **`pgs_app_data_db`**. Браузер
   не умеет открывать TCP к Postgres, поэтому запросы обслуживает backend-прокси
   **`server.js`** этого репозитория (тот же паттерн, что и у дашборда opti).

Соответствие версий между источниками: база ClickHouse `data_public_2` ↔ схема
PostgreSQL `public_2` (снимается префикс `data_`, регистр не важен).

Подписи версий при подключении ClickHouse автоматически читаются через backend
из базы **`pgs_app_metadata_db`**, таблицы `scenario`: цифровой суффикс имени
ClickHouse-базы после последнего `_` сопоставляется с `scenario.sys_id`, а
пользователю показывается `scenario.name`. Текстовое название версии из
сценариев показывается во всех разделах дашборда: подпись активной версии в
шапке, список версий и подсказки в модалке подключения, «Сравнение версий»
(колонки матрицы, селекторы базы и разложения, резюме), заметки загрузки в
значке ⚠ (включая строку «Версии: …»). Поиск в списке версий работает по
названию, номеру и техническому имени базы. Если metadata-БД, таблица или
соответствующая запись недоступна, используется прежняя логика: название из
`scenario.xlsx` (если загружено), иначе техническое имя схемы.

## Быстрый старт

```bash
npm install
npm start        # → http://localhost:8080 (PORT/HOST настраиваются переменными окружения)
```

`server.js` одновременно раздаёт статику дашборда и API PostgreSQL:

| Эндпоинт              | Назначение                                                        |
|-----------------------|-------------------------------------------------------------------|
| `GET  /api/health`    | проверка, что backend жив                                         |
| `GET  /api/pg/defaults` | хост/порт/база PG по умолчанию для формы подключения            |
| `POST /api/pg/schemas` | схемы, в которых есть таблица `independent_demand`               |
| `POST /api/pg/scenarios` | названия версий из `pgs_app_metadata_db.scenario` (`sys_id` + `name`) |
| `POST /api/pg/unc`    | агрегат неограниченного спроса: `{schema, gran}` → итог и периоды по `Σ demandqty` |

Логин/пароль PostgreSQL вводятся в модалке подключения (блок «PostgreSQL —
independent_demand»), уходят в теле каждого запроса и нигде на сервере не
сохраняются; в браузере — автосессия на 4 часа (кнопка «Забыть PG-сессию»).

Открытие `index.html` напрямую (или со статического хостинга) тоже работает:
ClickHouse-подключение не требует backend. Для PostgreSQL в этом случае укажите
в модалке поле **«Backend»** — URL запущенного `server.js` (при `file://`
подставляется `http://localhost:8080`).

> **Важно про PostgreSQL.** Запросы `/api/pg/*` уходят на тот адрес, с которого
> открыта страница. Если дашборд открыт не с `server.js` (статический хостинг,
> превью, другой порт), на них отвечает чужой сервер — обычно `404 Not found`,
> и неограниченный спрос молча уходит в фолбэк `demand_coverage`. Поэтому
> открывайте дашборд по адресу запущенного `server.js` (`http://localhost:8080`)
> либо впишите его адрес в поле **«Backend»**. Со страницы по HTTPS браузер не
> пустит запрос на `http://localhost` (mixed content) — тогда вариант один:
> открыть сам `server.js`.
>
> Процесс `server.js` должен видеть PostgreSQL по сети: продуктивный хост
> `db-postgresql-app.k8s…in-plan.ru:48235` доступен только изнутри контура,
> поэтому backend запускают на машине в этом контуре (ноутбук в VPN, под в
> Kubernetes), а не на внешнем хостинге.

Дашборд сам проверяет backend (`GET /api/health`) и различает три ситуации:
backend не найден по адресу → «нет backend-прокси, запустите `npm start`»;
backend ответил, но не знает эндпоинт → «обновите `server.js`»; ответил с
ошибкой Postgres → показывается текст Postgres (неверный пароль, нет схемы,
нет прав). Схема подбирается терпимо: `Data_public_4899` → `public_4899`
(регистр, префикс `data_`, однозначный номер версии), а если схемы нет —
в ошибке перечислены схемы, которые в базе есть на самом деле.

### Соответствие версий ClickHouse и схем PostgreSQL

По умолчанию схема подбирается по имени: `data_public_2` → `public_2` (регистр и
префикс `data_` не важны, однозначный номер версии тоже подходит). Но нумерация
прогонов в ClickHouse и схем в Postgres совпадает не всегда — например, в CH
выбраны `Data_public_4899` и `Data_public_4941`, а в `pgs_app_data_db` схемы
идут `public_13`, `public_135`, `public_1494`, `public_1545`…

Поэтому в модалке подключения, в блоке **«Соответствие версий и схем
PostgreSQL»**, под каждой выбранной версией стоит список всех схем с
`independent_demand` (с оценкой числа строк). Строка сразу показывает результат
автоподбора — `✓ public_4941` или `схемы «public_4899» нет — спрос из
demand_coverage`, — а выбранная вручную схема имеет приоритет над автоподбором,
сохраняется в автосессии и отправляется на backend с флагом `exact`, чтобы
сервер не подставил «похожую».

### Предупреждения загрузки

Проблемы источников больше не печатаются красной простынёй в шапке: в правом
верхнем углу появляется значок **⚠** (его нет, когда всё загрузилось чисто).
По клику — панель с разбором: что недоступно, по какой причине, у каких версий
и что сделать, плюс кнопка «Открыть подключение».

## Неограниченный спрос — источники

1. **PostgreSQL** через backend-прокси — схема `public_N` по CH-базе
   `data_public_N`. Таблица `independent_demand` (legacy-алиас: `independentdemand`)
   физически лежит только там (в ClickHouse её нет — дашборд туда и не ходит).
   Единственная колонка объёма спроса — `demandqty`. Backend читает только
   ключевые столбцы `item`, `demandqty`, `periodid`, `dmdstream`, `periodtype`,
   `demandtype`, `loc`, `date`; служебные `sys_id`, `update_date_time`,
   `change_author`, `unit`, `adjusteddemandqty` в SQL не участвуют;
2. фолбэк между источниками: покрытый + непокрытый
   (`fullfilleddemandqty + unfullfilleddemandqty`) из `demand_coverage` — когда
   PostgreSQL/схема/таблица/колонка недоступны **или** PostgreSQL прочитан, но
   `Σ demandqty = 0` и покрытие доступно. Нулевой PG-вход всё равно фиксируется
   в предупреждении загрузки; при пустом `demand_coverage` сохраняется ноль.

Какой бы источник ни сработал, значение лежит в `agg.totals.cov.demUnc`, и все
разделы читают одно определение; фактический источник фиксируется в
`agg.totals.uncDetail` («PostgreSQL · public_2»).

## Счёт заказов и стадии водопада

Если backend API 7+ отдаёт построчный `independent_demand`, количество заказов
считается по полному входному реестру. Строки сопоставляются с `marking_demand`
по товару, локации, типу и потоку спроса; отсутствующие в плане добавляются в
RCA как «100% не покрыто». Для старого backend сохраняется агрегатный режим
`demand_coverage`. «Частично покрыто» означает наличие и отгрузки, и дефицита,
«полностью покрыто» — отсутствие дефицита при ненулевой отгрузке.

Заказ считается «Отгружено с опозданием», если для его бизнес-ключа в
`demand_cost`/`demand_cost_ti` задано `latedelivperiods > 0`, а период отгрузки
в `marking_demand` позже срока `periodid`/`date` из `independent_demand`.
Поэтому «План продаж» = «В срок» + «Отгружено с опозданием». В водопаде
«План продаж» объединяет полностью и частично выполненные заказы: выполненная
часть синяя, дефицит частично выполненных заказов — жёлтый сегмент. Отдельного
фильтра RCA «Дефицит плана» нет; единый фильтр «План продаж» показывает обе
группы. Водопад спроса имеет режимы «Тонны» и «Заказы»; клик по столбцу или чипу стадии фильтрует
RCA-таблицу по заказам этой стадии. Единая точка классификации —
`covBasis(D).ord` в `index.html`; без `demand_coverage` используются
агрегаты `marking_demand`, под фильтрами — загруженная выборка (детали и
тождества — в CODE_AUDIT.md, §22).

### План продаж и 100% непокрытый спрос в интерфейсе

- По умолчанию все релевантные графики, **кроме водопада спроса**, строятся
  только по **«Плану продаж»**: полностью и частично покрытым заказам. Строки
  со статусом «100% не покрыто» не попадают в график автоматически.
- **Водопад спроса** («Спрос и покрытие») по умолчанию открывается в режиме
  **«Все заказы»** — цепочка «от неограниченного к отгрузке в срок» читается
  целиком сразу; переключатель может вернуть его к «Плану продаж» (водопад
  тогда начинается с ограниченного спроса).
- У графиков, где сравнение осмысленно (`o8`, `d1`, `d2`, `d8`, `d9`), есть
  собственный маленький переключатель охвата из трёх положений:
  **«План продаж» / «Все заказы» / «100% непокрытые»**. Он меняет множество
  заказов только этого графика и не затрагивает KPI, таблицы, фильтры или
  соседние графики. В режиме «100% непокрытые» на графике остаются только
  заказы со 100% непокрытым спросом (`fullfilleddemandqty = 0`). Финансовый
  факт (выручка, себестоимость, валовая маржа) всегда остаётся в охвате
  Плана продаж.
- KPI полностью покрытых заказов в «Общем» называется **«Заказов выполнено»**.
  Это `fullyCoveredOrders / orderRows` из полного входного реестра, с фолбэком
  на классификацию `marking_demand`/загруженной выборки.

### Периоды, ID и единая экономика потерь

Календарный `periodid` PostgreSQL (`4YYYYMMDD`, `YYYYMMDD` или дата) не
показывается как техническое имя вида `P420270401`. При объединении реестров
совпавшие строки `independent_demand` ↔ `marking_demand` создают мост даты к
бакету Плана продаж; непарные 100% непокрытые строки получают тот же
канонический бакет `P0`, `P1`, … по позиции в горизонте. `periodLabel()`
используется фильтрами, графиками и таблицами как единый formatter.

У непарных входных строк нет `order_id`, поэтому внутренний отрицательный ID
скрыт. RCA и «Данные → Заказы спроса» показывают одинаковую стабильную метку
`ID-N`; обычные заказы — `№<order_id>`. Общая часть колонок этих таблиц имеет
одинаковые названия, статусы, периоды и формулы.

`lmState(D)` является общей точкой расчёта для «Общего», «Спроса и покрытия»,
RCA и «Заказов спроса». Упущенная маржа и упущенная выручка считаются по
единой базе «Непокрытый спрос» — полной цене отказа (дефицит плана + спрос,
не принятый в план); выбор базы отменён, переключателя нет. Если
неограниченный спрос недоступен (нет `independent_demand`/`demand_coverage`,
нулевой объём, активны фильтры), расчёт автоматически возвращается к
«Дефициту плана», а подсказка «?» карточки объясняет причину; значение по
второй базе всегда видно там же. Оценка 100%-непокрытой группы — компактный
переключатель «Метод» над карточками обеих вкладок (два варианта: «Ставка
минус себестоимость» / «Средняя маржа по продукту», сохраняется в
`localStorage`). Плановый дефицит и непринятый в план спрос распределяются
раздельно по своим строкам; остаток при ограниченной детализации показывается
отдельно. Для 100% непокрытых строк `price`/`mpt` — только оценочные ставки
потерь, а фактические `rev`, `cost` и `mar` равны нулю: неисполненный заказ
не считается продажей.

Сообщение вида «Σ demandqty = 0 при periodtype 4 (строк: 210)» означает, что
backend и PostgreSQL **доступны**, схема и таблица найдены, но после фильтра и
дедупликации по ключевым столбцам `Σ demandqty = 0`. Перед таким сообщением
backend дополнительно сверяет непустой результат построчно с тем же набором
210 строк — это защищает от ложного нуля, если `SUM` в представлении или
нестандартном типе PG вернулся как `0`/`NaN`. Если построчные значения дают
ненулевую сумму, именно она и периодный разрез попадают в ответ как
`demandqty`; источник не подменяется `demand_coverage`. Если и построчная
сумма равна нулю, при доступном `demand_coverage` используется его фолбэк,
а причина нулевого PG-входа остаётся в предупреждении загрузки. Если покрытия
нет или оно пустое, дашборд сохраняет нулевой вход и сообщает об этом отдельно.

## Разворачивание в контуре

Процесс Node должен видеть и PostgreSQL (для API), и быть доступным
пользователям дашборда. Типовой вариант — рядом с базой PG в том же
Kubernetes-контуре: `HOST=0.0.0.0 PORT=8080 npm start`. ClickHouse браузер
пользователя подключает напрямую — сетевой доступ к нему нужен с машин
пользователей, к backend — только к порту Node.
